# 11-channel sampling rate verification

COM17, ESP32-S3 84:c7:bb:56:2f:10. Firmware flashed and write hash verified.

Changed I2C to 400 kHz, removed the TCA9548A post-STOP scheduler delay, disabled full serial CSV, set MPU internal updates to 100 Hz and frame target to 20 ms. HTTPS batch maximum is 25 frames. Frame timestamp is the midpoint of the sequential read window; it is not a hardware-synchronized conversion time.

At 100 kHz after removing the delay, scans averaged about 21.7 ms, exceeding the target. At 400 kHz, all 11 channels were detected. Stable scan means were 7.0–7.8 ms. Observed stable-window maxima reached 36 ms with networking; first HTTPS connection caused a larger 897 ms stall. Timing is therefore not hard real time.

Server session e5f68d925b7d50be: final checked 20-second window contained 1001 frames, mean interval 20 ms (50 Hz), min 8 ms, max 44 ms, p95 23 ms, no sequence gaps, valid_mask=2047 throughout. Serial logs showed 549 startup dropped frames before the uploader caught up; this count did not increase during the later observation. Do not describe this as a loss-free boot or guaranteed 50 Hz under every network condition.

HTTPS uploads successfully persisted to SQLite, but upload buffering and network latency remain distinct from sample timing. At 50 Hz a full 25-frame batch covers roughly 0.5 seconds. For model inference requiring low latency, a persistent transport and tighter acquisition/network task isolation should be evaluated separately.
